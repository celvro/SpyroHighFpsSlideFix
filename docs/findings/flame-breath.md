# Flame breath stray lines (reported 2026-09-15 as "flames spread much farther to the side at high FPS"; cause found and fixed 2026-09-16)

- `GA_Spyro_FireAttack` spawns a pooled `FireAttackActorTrace_C`, a Blueprint on native `SpyroFlameBreathActor` (`/Script/Falcon`). `InitFireAttackActor` sets `FlameEmitterTemplate` to `PS_VFX_Flame_Breath` (`_Rage` with rage fire) and `ImpactEmitterTemplate`. The native actor traces `TraceEndPoints` (150,0,0), (140,∓25,0), (120,∓48,0) (radius 15) and sets float parameters `SP_Flames_C/L1/R1/L2/R2` (`MinParticleParameterVal` 0.01, `HideFlameEmitterThreshold` 5, `MuzzleThreshold` 60). Its per-frame code is native and unread.
- `PS_VFX_Flame_Breath` (`VFX_Spryo/Shared/Particles/Characters/Spyro/FlameThrower`) has 23 sprite emitters (`flames_velocity_L1/L2/R1/R2`, `flames_cards_*`, `Flames_*_Card`, muzzle, motes), some LOD levels disabled. Emitter lifetimes are `DistributionFloatParticleParameter`s of those parameters (input 0.01–1 → 0.001–0.25/0.275/0.3 s), so each side's flame length follows its trace.
- Framerate suspects in the emitters: `ParticleModuleAttractorPoint` per side emitter (e.g. position (50, −100, −20), range 150, strength 1200; another (50, 0, −20), range 80, strength −300), all with `bAffectBaseVelocity` and `bOverrideVelocity`; `AccelerationDrag` coefficient 2 (`bAlwaysInWorldSpace`); `VelocityInheritParent` 0.7 in world space; start velocities up to (1200, ±300, ±100); EmitterDuration 0.3–0.4, EmitterDelay 0.05. Whether 4.19's AttractorPoint update (with those flags) scales by DeltaTime isn't confirmed; disassembling it needs the decrypted `.text` from a running game (see `docs/findings/fire-dragon.md`).
- Player report after a first test (2026-09-15 15:47–15:49): the wide spread seemed to happen **more often uncapped (~385 FPS) than at 144**, so it looks intermittent and gets worse the higher the framerate. That session's probe logged no sizes: the flame components were found (the native actor creates a new `ParticleSystemComponent` per breath, owned by `FireAttackActorTrace_C_N`), but the `GetComponentBounds` out-params weren't where the probe looked, and the error stopped the flame update every frame.
- Second test (15:59–15:59:52, `flames_20260915_155842.csv`, 9 breaths at 144 FPS and 5 at 30, standing still, yaw −177): **the world bounds are unusable.** On 50–95% of active frames the box includes the world origin (reach ~331,000 at 144 and ~1,777,000 at 30, most likely from emitters with no particles). The remaining frames are near-cubes with extent ≈ 355–526 on all three axes, i.e. particle size padding and not the flame's shape. `SP_Flames_*` stayed 1.0 throughout at both rates (sometimes missing from `InstanceParameters` on a frame), so the native trace isn't what widens the flame. Uncapped wasn't tested that session.

- K experiment ran 16:10–16:11 (all modes cycled three times, templates found, module counts as expected); the visual result wasn't reported yet.
- **Disassembled from the running game (16:12, `tools/Read-GameVtables.ps1`):** particle module vtable slot 71 is `Spawn`, slot 72 is `Update` (slot 0 destructor, 9/15/70/79/101 other overrides). None of these three suspects has a framerate bug:
  - `ParticleModuleAttractorPoint::Update` (RVA 0x1521610): attractor position and range from `Owner->EmitterTime`, transformed to world (and range/strength scaled by the component scale) unless the emitter is local space or `bUseWorldSpacePosition`. Per live particle within range: Dir = normalize(position − Location); strength = Strength(EmitterTime) or, with `StrengthByDistance`, Strength((range − dist)/range); a negative strength flips Dir; Dir components are clamped by the Positive/Negative axis flags; then **Velocity += Dir·strength·DeltaTime**, and BaseVelocity too if `bAffectBaseVelocity`. `bOverrideVelocity` isn't read. That's plain frame-time-scaled acceleration.
  - `ParticleModuleAccelerationDrag::Update` (RVA 0x1520780): per particle **Velocity += −Drag(RelativeTime)·Velocity·DeltaTime**, and the same amount to BaseVelocity. First-order correct at any framerate (drag 2).
  - `ParticleModuleVelocityInheritParent::Spawn` (RVA 0x154F620): Velocity and BaseVelocity += Scale(EmitterTime) × component `PartSysVelocity` (offset 0x6FC; a reflected property, next to `OldPosition`), rotated into local space for local-space emitters. The flame component's position per frame (`flames_20260915_155842.csv`) is smooth at 144 FPS (head motion, mostly < 500/s; ~290 while walking). About 0.6 s into a breath it jumps to the world origin and stays there while still active (the ~120 "zero movement" frames), so `PartSysVelocity` is huge on that one frame (≈6·10⁷ at 144, 1.3·10⁷ at 30) but smooth otherwise.
  - Other overrides seen: AccelerationConstant Spawn 0x151C7D0 / Update 0x151FE80, Velocity Spawn 0x154F5C0, Drag slot 79 0x1518AF0.
- **Visual A/B result (player, 16:10–16:11): no mode changed the spread** (attractor, drag, inherit-parent or constant acceleration off); the flames were maybe less bright with AccelerationConstant off. So the module math is ruled out, which matches the disassembly.
- **Screenshots (2026-09-15, Steam `flame-30fps.jpg` / `flame-unlimited-fps.jpg`, standing still facing world −X):** the main fan is about the same size at both rates. Uncapped adds **two long, thin, faint orange streaks at ~45° either side**, reaching past the scorch mark, and the flame tongues look thinner and more separated. 30 FPS is a fuller fan with no streaks.
  - Hypothesis (untested): float32 world position quantization, the same class as the sliding bug. World-space emitters integrate Location += Velocity·dt each frame at x,y ≈ −300,000 (1/32 spacing), so small per-axis steps round to 0 or whole steps, e.g. 12 units/s per step at ~385 FPS, 4.5 at 144, 0.94 at 30. Slow, drag-damped particles then move and orient along lattice directions such as exactly 45°, and the long velocity-aligned (`PSA_Velocity`) sprites show that as streaks. That's worse uncapped than at 144 and invisible at 30.
  - Test: the probe's K experiment now has `localSpace` (every flame emitter's `RequiredModule.bUseLocalSpace` on, so positions are small and unrounded; judge breaths while standing still) and `tick30` (`SetComponentTickInterval(1/30)` on each flame component, a candidate fix that simulates particles at 30 FPS steps).
- **K experiment result (16:34–16:35, uncapped):** `normal` and `localSpace` both show the same two lines sticking out farther than the rest, so **the float quantization hypothesis is wrong** (the log confirms 28 RequiredModules flipped). `tick30` removes them but visibly animates at 30 FPS. So it's step-size dependent, but only one or two stray long sprites per breath are affected, not the whole fan.
- Player bug report screenshot (`flame-nexus-bug.jpeg` in the repo root, 239 FPS, not reproduced by the player): next to a normal fan, one long flame sprite points backwards over Spyro's back (straight up the screen) and one points straight out to his left.

- **Particle capture 2026-09-16 16:27 (`build/probe/flame_particles.csv`, 3 breaths at 320 FPS, 3 at 30, standing still).** `EmitterInstances` is at component +0x860. Emitter indices follow the template's `Emitters` order (20 `hard_flames_velocity_muzzle`, 21 `flames_velocity_Muzzle`, 22 `mesh_muzzle`).   - The world-space emitters simulate the same at both rates (speeds ~200–1100, side lobes at ~50° from the attractors). There are no odd velocities or positions at 320 FPS.
  - At 30 FPS every world-space emitter's first burst of 5 gets velocity ≈ (−6.3M, −6.3M, +12k), the `PartSysVelocity` spike from the component moving from the world origin to the mouth (×0.7). It's still active at the tick that crosses the 0.05 s EmitterDelay, so those bursts fly hundreds of thousands of units away within a frame and are never seen. At 320 FPS the delay spans ~16 frames, the burst gets a normal velocity (~760 forward) and is visible. (A difference, but not the lines.)
  - **Emitter 20 (`hard_flames_velocity_muzzle`, local space, `PSA_Velocity`, rate 80 + burst 5, ~22–26 alive)** simulates identically at both rates: velocity ≈ (8–10, ±2, ±0.5) local, sprites growing to 40×240. But its per-frame move is **~0.022 units at 320 FPS vs ~0.30 at 30**. The velocity-aligned sprite direction comes from that per-frame move, so at high FPS it's unstable (float resolution or the renderer's normalize threshold, not pinned down since the shaders weren't read), and the long thin sprites snap to arbitrary axes. That fits every test: the module A/B didn't touch it, `localSpace` didn't change it (already local), `tick30` fixed it (bigger per-tick moves), and it's worse the higher the FPS. Emitter 21 (`flames_velocity_Muzzle`, local, 86–250 units/s, ~0.3–0.8 units per frame at 320) is a weaker suspect.
  - K experiment 16:33–16:35 (player, 320 FPS; log confirms each mode applied): `normal` shows lines straight up and right; **`noHardMuzzle` (emitter 20's LOD off) fixes both**; `noMuzzleVelocity` (20 and 21 off) also fixed; `rotateX` / `rotateY` (20 and 21 with `PSA_Rectangle` + `AxisLockOption` `EPAL_ROTATE_X`/`_Y`) left one line straight up. **Cause confirmed: `hard_flames_velocity_muzzle`.** A rotate lock makes the lock axis the sprite's width and its length perpendicular to the lock axis and the camera, i.e. vertical with the camera behind Spyro, so axis locking can't replace velocity alignment here. Enum values from the exe string order: PSA_Rectangle 2, PSA_Velocity 3, EPAL_ROTATE_X 7, _Y 8.

- **Fix `FIX_FLAME_MUZZLE_LINES` in `HighFpsSlidingAndJumpFix`.** The emitter has no gameplay role: its modules are only lifetime, size, velocity, color, SubUV, dynamic parameter, drag and pivot (no collision or event modules); the only collision settings in the asset are the GPU `flame_motes` sparks' visual depth-buffer collision, and flame damage comes from the native actor's traces.
  - **Current version (velocity scaling, deployed 2026-09-16, not yet verified from the mod itself):** with the smoothed frame time `avgDt = 0.9·avgDt + 0.1·dt`, it multiplies every value of the `ParticleModuleVelocity` StartVelocity lookup table (`StartVelocity.Table.Values`) on every LOD of `hard_flames_velocity_muzzle` in `PS_VFX_Flame_Breath` and `_Rage` by k = max(1, (1/30)/avgDt), from the originals read when the template is found. It rewrites when k differs from the written scale by > 10% (`FLAME_VELOCITY_RESCALE`), and restores exactly at k = 1. It logs `velocity scaled xK / restored in <template>` only when switching between scaled and unscaled. On error it restores the originals and disables itself.
  - Caveat: originals are read from the live template, so a hot reload while scaled (or after the probe's `velocity30`) would take scaled values as originals and compound. Restart the game instead. Don't use the probe's K experiment with the fix on.
  - Previous version (**verified 2026-09-16 16:56–16:57**, lines gone at 320 FPS): set `bEnabled` false on every LOD of the emitter when avgDt < 1/35 s. It only affected the next breath, and the flame looked a little less full at high FPS.
  - Template lookups: one at startup, then `NEW_OBJECT_LOOKUPS` after `NotifyOnNewObject("/Script/Engine.ParticleSystem")` reports a template by name; a found template with no `Emitters` yet keeps retrying.
