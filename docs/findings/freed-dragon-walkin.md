# Freed dragon walk-in (Spyro 1; cause found from assets 2026-09-17, fix verified 2026-09-17)

Reported: at high FPS, Spyro doesn't walk into place after touching a dragon statue, but does at 30 FPS.

- `GameplayCommon/LevelMechanics/Collectable_Dragon/Collectable_Dragon`: on touch, `MovePlayerSeq(0)` calls `NavigationSystem.SimpleMoveToLocation(PlayerController, Walk to Target Point)`, then `Delay 1`. `MovePlayerSeq(1)` checks the distance to the point: under 50 it calls `StopMovement` and `MovePlayerSeq(2)` (turn to face the dragon, `A_CP1999_Spyro_cinematic_turn_right`); otherwise it waits 0.25 s, re-issues the move and checks again, forever.
- Path following moves Spyro through the CMC's `RequestedVelocity` with **zero input acceleration**, so `fixWalkingVelocity` treated it as braking. From rest, the first path step at 144 FPS is 1000·dt² = 0.048 units, which rounds to 1/32 per axis (velocity 4.5), within the fix's quantization tolerance (4.54) of the braking prediction 0, so the fix wrote velocity 0 back every frame and Spyro never started. At 30 FPS (tolerance 0.95, step 33) and 60 it doesn't trigger. Likely a mod bug, not vanilla, at 144 FPS; the unmodded engine should also stall from rest above ~250 FPS (the standstill rounding).
- First fix, tested 2026-09-17 02:26–02:27 (144 FPS): skip the walking fix while `cmc.RequestedVelocity` is nonzero. Lua can read it (`started`/`ended` logged), and he walked, but then **slid slowly near the target**: `RequestedVelocity` stays set after the path reaches its goal (one move logged `ended` 4.5 s later, the next never did), so the braking fix stayed paused through the high-FPS slide.
- Second fix, tested 02:36 (~260 FPS judging by log timing): a nonzero velocity from rest with no input can't be braking rounding (braking from 0 is exactly 0), so `fixWalkingVelocity` followed the engine until its velocity was within tolerance of braking from its previous-frame value for 3 frames. It ended 11 ms after the start at speed 8.8: at ~260 FPS the tolerance is ~8 per axis but a frame adds only ~4, so early acceleration looks like braking.
- Third fix, tested 02:44 at ~470–550 FPS (trace `trace_20260917_024357.csv` in the probe folder): same no-input start, following the engine until the speed stopped rising below 0.9·MaxWalkSpeed. The fix wrote nothing during the walk, but **the engine's own path move fails at that rate**: several starts gave one frame at speed 1.78 (= 1000·dt) and then 0 (the step rounds to nothing), so the walk began ~0.25 s late; once moving, the speed sat at 100–200 on lattice values (vx exactly 0 for long stretches) instead of 268, heading off the straight line. The player saw him reach the spot only near the end of the unfreeze animation; 1.23 s after the walk started the cutscene hid and teleported him (the Level Sequence runs in parallel, so the walk has a time budget).
- Current fix: predict the path move like input acceleration. While `RequestedVelocity` is nonzero **and** the controller's `PathFollowingComponent:GetPathActionType()` is ≥ 2 (DirectMove/PartialPath/PathToGoal; the stale RequestedVelocity after arrival goes with status Idle → NoMove), `calcRequestedWalkingVelocity` mirrors 4.19 `ApplyRequestedMove` + `CalcVelocity`: speed = MaxWalkSpeed if `bRequestedMoveWithMaxSpeed` else min(MaxWalkSpeed, |request|); if `bRequestedMoveUseAcceleration` and below speed·1.01, friction-blend the direction (GroundFriction) and accelerate at (move − v)/dt clamped to MaxAcceleration, else set v = move velocity; brake only when over speed; clamp. The result goes through the usual tolerance check and write-back. Logs `walking fix: path following move started` / `ended`. 4.19 `FollowPathSegment` (non-acceleration paths) requests (point − feet)/dt with max speed on all but the last segment.
- **Tested 2026-09-17 03:12 at ~360–490 FPS** (trace `trace_20260917_030956.csv`; `path following move started` / `ended` logged, no errors): he started at once, accelerated at 1000/s to 268.5, walked 124 units straight and stopped 0.59 s after the request. The player said it looks mostly normal, except that he stands still for a moment before turning. The turn began 1.24 s after the request (the Blueprint's fixed `Delay 1`, then the turn montage ~0.2 s later), so a short walk leaves a ~0.65 s wait. That should happen at any framerate but hasn't been compared at 30 FPS yet; the player also suspects a slow dragon load (one 10.7 ms frame during the walk).
- Probe `walkin` lines (one per path following move): avgFps, maxDt, hitches (> 50 ms), the `Collectable_Dragon_C` (CutsceneActive, nearest) and distances to its `Walk to Target Point` (3D and 2D) at the start and on arrival, `moveAt`/`arriveAt` (s after the request), walked distance, maxSpeed, stalledFrames (path active at speed 0), `reissued` (moves re-requested after arriving ≥ 50 away), `wait` (arrival → end), `endedBy` turn (yaw rate > 30°/s while standing) / teleport (> 50 units in a frame) / input / timeout (5 s), and the dragon's `Level_Sequence` playback position at the start, on arrival and at the end.
- **Verified 2026-09-17 03:17** (Alban, `Collectable_Dragon_alban`, same spot, `walkin` lines): 30 FPS arrived at 1.267 s, turned at 1.467 (walked 283.3, 22.8 from the target); uncapped (~365 FPS) arrived at 1.205 s, turned at 1.462 (walked 284.4, 23.4 away). Max speed 268.5 and no stalls or re-issued moves at either rate. The earlier pause was just a short walk (124 units) finishing inside the fixed 1 s delay.
- Zoe after replays (03:18) was not a bug: talking to her worked, but her button prompt stayed on screen after a framerate change while Spyro was too far away to talk. It couldn't be reproduced. Her state machine (in `CNS1154_SaveFairy/Blueprints/SaveFairy`): `ZapCheck`, `Talk`, `NPC` and `HiddenIGC` have no native triggers, so Blueprint code has to move her out of them.
- Prepared for the final test and profiling run (03:25): `PROFILE = true` (**set it back to false before committing**), mod deployed without the probe (its garbage skews the profile). The path check (`readPathRequest`) runs on every frame without input, including standing still: one `RequestedVelocity` read, plus the path component call only while that's nonzero. It's called through `pcall` without a per-frame closure.
- **Final test and profile, 2026-09-17 12:22–12:29** (mod only, no probe, `UE4SS.log`, no errors): 7 walk-ins at high FPS (avg frames 1.2–3.2 ms, ~310–850 FPS; move durations 0.30–1.47 s) and 1 at 30 FPS (1.20 s). Each logged `path following move started` / `ended`, and the player saw him walk into place.
  - Fix cost per frame: 0.07–0.20 ms uncapped (4.5–6.9% of frame), 0.12–0.16 ms at 30 FPS. That's in line with the 2026-09-16 default-collector baseline (0.10–0.17 ms uncapped, 0.05–0.13 at 30), so the path check adds no visible cost.
  - Max per 10 s window: 0.2–7 ms in most windows, but 12.0, 13.4, 27.7, 30.8 and 39.8 ms in five windows, larger than the 4.2–9.4 ms collection hitches measured on 09-16. Two of them landed within ~4 s after a walk-in starts (the dragon cutscene loads then) and three didn't. Not attributed (no `GC_PROFILE` this run); the first window's 14.6 ms is the known startup lookup miss.
  - `PROFILE` set back to false afterwards.
