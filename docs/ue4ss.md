# UE4SS (runtime Lua modding)

- UE4SS experimental build `v3.0.1-1133-gb4cefa18` is staged in `tools/bin/ue4ss-dist/` (gitignored). `tools/Install-UE4SS.ps1` installs it (`dwmapi.dll` + `ue4ss/` in `Falcon\Binaries\Win64`) and deploys `ue4ss/Mods/*` (player-facing fixes) with `enabled.txt`. `ue4ss/DevMods/*` (the probe) is deployed only with `-Probe`; without it, a previously deployed probe has its `enabled.txt` removed (its traces stay in the game dir). Use `-ModsOnly` after editing Lua, and `-Uninstall` to remove everything. The installer sets engine version 4.19, turns on the external console, and enables both hot reload (Ctrl+R) and auto-reloading of Lua mods (saving a file under a mod's `Scripts` folder reloads that mod), so `-ModsOnly -Probe` picks up a Lua change without a restart. That needs the patched `UE4SS.dll` in the dist (`tools/ue4ss-patches/luamod-hot-reload-actions-mutex.patch`, built from source; see `tools/bin/ue4ss-dist/VERSION.txt` and the entry in `docs/tools.md`). On the stock `v3.0.1-1133-gb4cefa18` DLL a reload crashed the game ("Fatal error!") — the probe's per-frame `LoopInGameThreadAfterFrames` hit it on the first reload every time, and the earlier ntdll+0xFA7D access violation right after a reinstall was the same race; with the patch, 70 reloads in a level did nothing. Reloading `HighFpsSlidingAndJumpFix` still crashes about one reload in five to ten (heap corruption, no dump; see `docs/tools.md`), so `Install-UE4SS.ps1` only copies files whose contents changed: editing the probe reloads just the probe. `tools/Restart-Game.ps1` (~12 s back into the level) is the way out when a reload does go wrong. Crash dumps land in `%LOCALAPPDATA%\Falcon\Saved\Crashes\*\UE4Minidump.dmp`; read them with `build/DumpInfo/DumpInfo.exe <dmp>` (source in `tools/DumpInfo`), which prints the exception and module-relative stack values; pipe that through `tools/Resolve-Ue4ssStack.ps1` to turn `UE4SS.dll+0x...` into function names (needs the local build's `UE4SS.map`).
- Profiling: set `PROFILE = true` in `HighFpsSlidingAndJumpFix/Scripts/config.lua` (all the `FIX_*` and profiling toggles live there). Every 10 s it logs `profile: N frames (avg frame X ms), fixes avg Y ms (Z% of frame), max, clock overhead` to `UE4SS.log`. Timing uses `GameplayStatics:GetAccurateRealTime`: UE4SS fills plain out-params into the passed table under the parameter name, e.g. `seconds.Seconds`, and `os.clock` only has 1 ms resolution. This excludes UE4SS's own hook overhead; measure that externally by comparing frame times with and without `dwmapi.dll`. Hook callbacks wrapped in `profiler.wrapHook` get their own `profile hook <name>` line per window (calls, ms/frame, ms/call, max).
- Profile baseline (v1.0.0, 144 FPS VSync, 2026-09-13): fixes avg 0.13–0.20 ms/frame (1.9–2.8% of 6.95 ms), max 0.8–2.7 ms per 10 s window, clock overhead 0.009 ms. Suspected cause: `UEHelpers.GetPlayerController()` runs `FindAllOf("PlayerController")` on every call, creating per-frame garbage. The mod now caches the controller and gameplay statics, and reads mode and velocity once per frame. After caching: running/jumping windows 0.017–0.059 ms avg, but standing still 0.107–0.113 ms, because the braking path still called GetCurrentAcceleration/IsPlayingRootMotion/K2_GetActorLocation at zero velocity. It now exits early at zero velocity. **Result (22:15 session):** 0.019–0.026 ms avg in every window, including standing still (~0.35% of a 144 FPS frame). Max per window 0.5–2.1 ms even at idle, when the tick does almost nothing, so the spikes aren't the fix logic. Jumps still +84.68. Jump apex (+84.68) and stops (≤0.17 s) were unchanged by the caching refactor. Max per window stays 0.2–3 ms, likely Lua GC or thread preemption inside the timed region.
- Profile v1.1.0 (2026-09-14 21:23–21:26, all fixes, 144 FPS VSync, normal play): fixes avg 0.08–0.15 ms/frame (1.2–2.2%), max 0.2–4.6 ms per window. Windows with loading hitches (7.2–7.6 ms average frames) peaked at 9–11 ms, and uncapped ~385 FPS windows averaged 0.03 ms. That's about 4–6× v1.0.0, and it hasn't been optimized yet. Per-frame work added since v1.0.0 includes FollowCamera/m_ctrInterp property reads and writes, the Charge_GroundEffects read, and IGetIsCharging plus the mouse predicate while MaxWalkSpeed ≥ 350.
- **Module split regression check, 2026-09-18 00:41–00:47** (all fixes, no probe, uncapped, 40 windows / 160,844 frames, avg frame 2.50 ms ≈ 400 FPS): fixes avg **0.143 ms/frame** (0.104–0.195), 5.72% of frame (4.3–7.7%). Max per window 0.26–0.5 ms in 27 of 40 windows, with outliers 26.9, 36.9 and 42.9 ms; the menu/loading window averaged 0.006 ms (no pawn) and peaked at 14.7 ms, the known startup lookup miss (14.6 ms on 09-17). That matches the 2026-09-17 pre-split run (0.07–0.20 ms, 4.5–6.9%, five outliers 12.0–39.8 ms), so the per-fix `pcall`s and the `ctx`/`config` table reads cost nothing measurable. No errors and no disabled fixes; both Blueprint hooks registered 14 s after load. Not sampled at 30 FPS this run (baseline there is 0.12–0.16 ms).
- `GetAccurateRealTime` out-params: the first profiling attempt found `PartialSeconds` missing from its own table, so `accurateSeconds` accepts either field from either table and logs both tables if one is still missing.
- **Profile and Lua GC runs, 2026-09-16 (all fixes including the flame fix, uncapped ~250–570 FPS, `PROFILE` + `GC_PROFILE`; restarts between runs).** Kept: the default collector, and profiling off in commits.
  - With the probe also running (17:01–17:03): fixes avg 0.09–0.17 ms/frame, max 17–27 ms in 4 of 14 windows. The probe's per-frame garbage makes collections land inside the fixes' timed region.
  - Default collector, no probe (17:08–17:10): avg 0.10–0.17 ms/frame (0.05–0.13 at 30 FPS). The mod allocates ~0.25–2.9 KB/frame (at 400+ FPS ~0.5–1 MB/s, mostly UE4SS wrappers for property reads and calls; the profiler itself adds a few tables per frame). The heap grows to 40–73 MB between collections, which free 2.4–12.5 MB each (0–3 per 10 s window). Windows with a collection maxed at 4.2–9.4 ms (roughly 1 ms per MB freed, not every max frame was the collection frame); windows without one maxed at 0.25 ms.
  - `collectgarbage("generational")` (17:13–17:15): worse. 0–1 collections per window freeing 5.6–37 MB, max 7–60 ms on those frames, heap up to 80 MB, avg 0.11–0.19 ms. The objects UE4SS returns probably have finalizers that keep them alive past minor collections.
  - `collectgarbage("incremental", 100, 200)` (pause 100, step multiplier 200; 17:20–17:22): no big collections (at most ~113 KB freed in a frame, max 3.1–5.4 ms), but avg cost rose to **0.44–0.72 ms/frame** (14–21% of a frame) and the heap still grew 1.6 → 25.5 MB. Not worth ~10–15% of the framerate.
  - Startup: on a normal start the druid montage and dragon function lookups each miss once, on the first frame with a `PlayerController` (menu/loading), ~20 ms together; 15–18 ms startup maxes matched that. Making them hot-reload-only was tried and reverted as not worth it (one-time, at boot). On level loads those lookups only start from `NotifyOnNewObject` on the levels that have the objects, and they hit.
  - An unexplained 47 ms max in the first window after load (17:20:25) showed 0.46 ms clock overhead, i.e. likely game loading.
  - Remaining option if the 4–9 ms collection hitches ever matter: allocate less per frame in the always-on fixes.
- **Per-fix allocation profiling (`PROFILE` + `GC_PROFILE`, added 2026-09-19).** Alongside the `gc:` line, each window now logs `gc alloc: T KB/frame (<fix> X.XX, ..., hook <name> X.XX, other X.XX)`: `main.lua` brackets every fix's `update` with `collectgarbage("count")` (`profiler.startAlloc`/`endAlloc`) and `profiler.wrapHook` does the same for hook callbacks, so the mod's KB/frame is charged to the code that allocates it. `other` is what the tick allocates outside the fixes (the `ctx` reads: `pc.Pawn`, `pawn.CharacterMovement`, `GetWorldDeltaSeconds`, `cmc.Velocity` — each UE4SS property read or call hands back a fresh table or wrapper). Frames where a collection lands inside a bracketed section have no attributable figure and are counted at the end of the line instead of guessed. The brackets only exist when both switches are on (`main.lua` swaps in the plain `run`), so a normal build pays nothing.
- **Allocation measurements, 2026-09-19 20:08–20:14** (all fixes, no probe, uncapped 280–1100 FPS, 34 windows, no errors and no disabled fixes). The mod allocates **1.98–3.40 KB/frame**, and the per-fix split is the same in every window, so the numbers are reproducible rather than noisy:
  - Idle (standing still, the steady state the last six windows sat in, identical to 0.01 KB across windows of 4238–4569 frames): **2.62 KB/frame** = camera centering switch 0.78, walking 0.64, charge dust 0.23, other (the tick's own `ctx` reads) 0.96.
  - Moving adds the fixes that only do work then: glide up to 0.44, charge fixes up to 0.35, camera centering up to 0.32. The jump fix never reached 0.01.
  - **It is nearly all UE4SS property wrappers, not Lua tables.** Dividing the per-fix figures by the reads each one makes gives a consistent price per UE4SS access: a **struct read ≈ 330 B** (`cmc.Velocity`, `GetCurrentAcceleration`, `K2_GetActorRotation`, `GetControlRotation`, `RequestedVelocity`), an **object property read ≈ 235 B** (`pc.Pawn`, `pawn.CharacterMovement`, `pawn.Charge_GroundEffects`), a **UFunction call ≈ 160 B**. A Lua table is ~80 B, so primitive reads and writes (`m_ctrInterp`, `GroundFriction`, `MovementMode`) cost nothing measurable. The ranked garbage list is therefore just a count of struct and object reads: camera switch 2 rotations (0.66), tick setup `pc.Pawn` + `pawn.CharacterMovement` + `cmc.Velocity` + `GetWorldDeltaSeconds` (0.96), walking `GetCurrentAcceleration` + `RequestedVelocity` (0.66), dust `Charge_GroundEffects` (0.23).
  - **The heap is not being collected back.** It climbed 8.7 MB → 392 MB over the session; the last six windows logged no collection at all (biggest per-frame drop 2.6 KB) while growing ~20 MB per window, i.e. faster than the ~12 MB the tick allocates in one (the Lua state is shared with UE4SS's own mods). Earlier windows did collect, and those are exactly the hitches: the 19.6 ms and 11.9 ms window maxima came with 12.6 MB and 21.7 MB drops, matching the ~1 ms per MB from the 09-16 runs. The 09-16 baseline saw collections at 40–73 MB; nothing in this session collected above ~160 MB, so a collection when it finally comes would be far worse. Whether that growth is retention (something holding references) or just the default pause ratio letting a big heap run has not been tested — a forced `collectgarbage("collect")` at a window boundary, logging the heap before and after, would separate the two.
- **Reads removed after those measurements, and what they were worth (2026-09-19 20:26–20:33, 35 windows, 30 FPS capped and ~300 FPS).** The per-item figures are framerate-independent — the camera switch fix read 0.78 KB/frame in both sessions to the byte — so they compare directly with the run above:
  - The dust fix only reads `Charge_GroundEffects` when `MaxWalkSpeed` says a charge is possible: **0.23 → 0.00** when not charging (0.02–0.14 while charging). On the frame a charge starts `MaxWalkSpeed` is still low, so the effect the hook then sees counts as new, which is the behaviour that was already wanted.
  - `engine.characterMovement` caches `pawn.CharacterMovement` per pawn address, the way the camera is cached, since a pawn keeps its component for its lifetime: `other` **0.96 → 0.73**.
  - Asking the path status before reading `RequestedVelocity` instead of after: **0.64 → 0.63, i.e. nothing**, and reverted. It disproved the 160 B estimate for a UFunction call: `GetPathActionType()` costs ~0.30 KB, about what the struct read it replaced costs, so **a call and a struct read are both ~330 B** and reordering only moves the cost around. The cheap nonzero test stays in front.
  - Idle total **2.62 → 2.14 KB/frame** (−18%). What is left is `camera centering switch 0.78` (two rotation reads), `walking 0.63` (`GetCurrentAcceleration` + the path query), `other 0.73` (`pc.Pawn`, `cmc.Velocity`, `GetWorldDeltaSeconds`). Every remaining item is a read whose result is needed every frame, so the next step would have to be sampling one less often (the stuck-camera gap) or finding a primitive property that answers the same question — `cmc.bHasRequestedVelocity` is the candidate for the walking fix's path query (a bool read is free), but whether the engine leaves it set the whole move needs a probe run before trusting it.
- **The heap growth is churn, not retention (`GC_FULL_COLLECT`, same session).** A forced `collectgarbage("collect")` at every window boundary put the heap back on its floor every time: 5063 → 3617 KB, repeated to the byte across 20 idle windows, and 19.9 → 11.9, 20.8 → 9.6, 17.1 → 8.1 MB in the moving ones (the floor tracks what the level has live). Nothing the fixes allocate is being held. So the 392 MB of the previous session was only churn the collector had not got to — Lua's default pause ratio letting the heap run — and the cost of collecting it confirms what that would have hitched: 1.7–2.1 ms to free 1.4 MB, 5.0 ms for 9.5 MB, 9.5 ms for 7.9 MB, 8.4 ms for 9.2 MB, i.e. the ~1 ms per MB of the 09-16 runs, which extrapolates to a ~400 ms stall had 392 MB ever been collected in one frame. A periodic forced collection is therefore a way to trade one predictable ~2 ms hitch for an unbounded one, if the hitches ever matter enough to ship a collector policy.
- **Per-frame garbage the fixes made, removed 2026-09-19** (all of it Lua-side, so it only changes how often the collector runs, not behaviour): the walking fix carried its predicted velocity in a fresh `{ x, y, z }` every frame and built a new table for each `cmc.Velocity` write and each path-following request; the jump fix did the same for its two velocity writes; the glide distance fix allocated an offset and a sweep out-param on every corrected frame; `spyro.isCharging`, the charge fix's mouse-steering query and the profiler's own clock reads allocated an out-param table per call (the mouse query also a closure per frame); `spyro.followCamera` read `pawn.FollowCamera` twice a frame, one wrapper each. These now use module-level tables cleared before each call, scalars, and a cached camera. Measured afterwards (above): worth roughly 0.1–0.3 KB/frame while moving, which is inside the spread of the 0.25–2.9 KB/frame baseline — the tables were real garbage, but at ~80 B each they were never the bulk of it. The cached `FollowCamera` is the one that shows up clearly, as it removed a 235 B wrapper per frame.
- `RegisterHook` on a **Blueprint** function in this build calls only the first (pre) callback, and it runs **after** the function body; the post callback never fires (measured on `BP_CPS1999_Playable_C:Charge_UpdateGroundEffects` and `:ReceiveTick`, 2026-09-14). A hook can't act before a Blueprint function runs or change its inputs. Register the same callback as pre and post, and make it idempotent.
- UE4SS Lua is 5.4, so `math.frexp`, `math.pow` and friends don't exist. A Lua error inside a per-frame loop only logs once (the mods guard with `errorLogged`), so check `UE4SS.log` for `error:` lines before trusting a test.
- Probe `drift` lines of ~0.15–0.2 s are normal stops: braking from full speed takes ~0.17 s. Multi-second drifts are the bug.
- The first AOB scan fails because the exe is still unpacking; the second pass succeeds (EngineTick hook found). Log: `Falcon\Binaries\Win64\ue4ss\UE4SS.log`.
